# 兩套引擎共用 KV 池服務多人

vLLM 與 SGLang 到 2026 年 10 月都用同一個 engine 進程同時服務多個使用者：所有請求進入同一條佇列與同一個 running batch，並向開機時就劃好的單一 GPU KV 池要記憶體，而不是按使用者各備一池。vLLM 把每個序列切成固定 token 數的 block，用 block table 把邏輯位置映到不連續的實體塊；跨請求重用走 Automatic Prefix Caching，以父塊 hash、本塊 token 與 extra key 組成的內容 hash 認領滿塊，而且 V1 預設開啟。SGLang 把 token 序列放進 CPU 上的 radix tree，節點只存 GPU pool 的 index，預設實作已是帶 FULL、SWA 與 Mamba 槽的 `UnifiedRadixCache`，最長相同前綴直接跳過 prefill。兩者預設都在 token 前綴相同時跨使用者共享 KV，沒有 per-user 配額；隔離必須由呼叫端帶入 `cache_salt`，SGLang 還可以用 `extra_key` 把樹拆開。池不夠時，沒人引用的前綴先按 LRU 讓出；仍在跑的請求則是 vLLM 丟掉 GPU block 並重算，SGLang 則 retract，而且不把這段 KV 插回樹。這些預設已經離開 2023 年 PagedAttention 與 2024 年 RadixAttention：前綴快取從論文裡的缺席或選用敘事變成預設、SGLang 的排程預設從 longest-prefix 改成 FCFS、搶佔也不再把 KV swap 到等量的 CPU block allocator。

## 同一進程的所有請求搶一塊事先劃好的 KV 池

PagedAttention 的切法還在。每個請求的 KV 被分成固定 token 數的 block，logical block 不必在 GPU 上連續，block table 把邏輯位置映到實體 block，attention kernel 分開抓取這些塊，而不是要求整段 KV 佔一塊連續顯存 ([Kwon et al., SOSP 2023](https://arxiv.org/html/2309.06180))。浪費被限制在最後一個未滿的 block：新的實體塊要等前面都滿了才分配。2026 年 10 月的 V1 把這個抽象收成單一 memory pool。只有 full attention 的模型時，所有層共用一張 block table；hybrid 模型按 attention 類型分成 KV group，sliding window 與 full attention 仍用同一池、同一 page size，只是視窗外的塊提早釋放 ([Hybrid KV Cache Manager](https://docs.vllm.ai/en/latest/design/hybrid_kv_cache_manager.html))。`--block-size` 在建構後一定是整數，但 latest engine arguments 沒有印出一個全域數字。v0.25.1 的類別常數是 **16**，未指定時部分 backend 會改掉它，例如 FLASHMLA 改成 **64**，所以不能把「CUDA 上永遠是 16」當成 2026 年 10 月的事實 ([Engine arguments](https://docs.vllm.ai/en/latest/configuration/engine_args/)；[CacheConfig v0.25.1](https://docs.vllm.ai/en/v0.25.1/api/vllm/config/cache/))。

池的大小在開機時就定死。`--gpu-memory-utilization` 預設 **0.92**，是這個 vLLM instance 的上限，啟動時用這個比例預先配置 GPU cache；同一張卡上的另一個 instance 不共享這份預算，要各自設定 ([Engine arguments](https://docs.vllm.ai/en/latest/configuration/engine_args/))。設了 `--kv-cache-memory-bytes` 就忽略 utilization。`KVCacheManager` 底下的 `BlockPool` 在初始化時一次建好全部 `KVCacheBlock`，free queue 用塊內的雙向指標，避免執行期再造 Python 物件 ([Prefix caching design](https://docs.vllm.ai/en/latest/design/prefix_caching.html))。服務多個使用者的方式不是每人一個 allocator，而是 V1 `Scheduler` 每一步把 running 與 waiting 混進同一次 forward，只向同一個 pool 要塊。註解寫明沒有獨立的 prefill phase 與 decode phase。Chunked prefill 在做得到時預設開啟，而且 **decode 優先**：先把待處理的 decode 放進 batch，`max_num_batched_tokens` 還有餘額才排 prefill，塞不下就把 prefill 切塊 ([scheduler.py](https://github.com/vllm-project/vllm/blob/main/vllm/v1/core/sched/scheduler.py)；[Optimization and Tuning](https://docs.vllm.ai/en/latest/configuration/optimization/))。進程分成 API server、一個放著 scheduler 與 KV manager 的 engine core，以及若干 GPU worker。Kernel 只看到每個序列的 physical block id，不處理跨序列的共享型態；共享發生在 scheduler 讓多張 block table 指到同一塊，並把 `ref_cnt` 加一 ([Kwon et al.](https://arxiv.org/html/2309.06180)；[prefix caching design](https://docs.vllm.ai/en/latest/design/prefix_caching.html))。

SGLang 的配置單位不同，共用方式相同。GPU 上的 KV 是 non-contiguous paged pool，CPU 上的 radix tree 只存 pool index，不存 tensor 本體；這點從 2024 年論文到 2026 年 10 月 14 日的程式沒有改 ([Zheng et al.](https://arxiv.org/html/2312.07104v2)；[radix_cache.py](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/mem_cache/radix_cache.py))。池的大小由 `--mem-fraction-static` 決定，對象是權重加上 KV pool。未設定時用 `(GPU 記憶體 − reserved) / GPU 記憶體`，偵測不到 GPU 記憶體則 **0.88** ([Server Arguments](https://docs.sglang.io/docs/advanced_features/server_arguments))。調參文件把這個比例寫成 `(權重 + KV pool) / GPU 容量`，其餘留給 activation 與 CUDA graph，經驗上留 5–8 GB 給 activation ([hyperparameter tuning](https://docs.sglang.io/docs/advanced_features/hyperparameter_tuning))。所有使用者進同一條 waiting queue、同一個 running batch、同一棵樹、同一個 pool。`--max-running-requests` 預設 `None`，是全域同時運行上限，不是 per-user 上限 ([Server Arguments](https://docs.sglang.io/docs/advanced_features/server_arguments))。當日 `main` 的工廠在 LMCache、pure SWA 等特例之後回傳 `create_unified_radix_cache`，所以預設樹是 **`UnifiedRadixCache`**：一個節點一段 token span，FULL 與 SWA 槽放 page index，Mamba 在前綴終點放 checkpoint，視窗外的 SWA 可以單獨變成空槽 ([registry.py](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/mem_cache/registry.py)；[Unified Radix Cache, 2026-10-12](https://www.sglang.io/blog/unified-radix-cache))。`--page-size` 預設 **1**，也就是一頁一個 token；大於 1 時，match、insert 與未滿頁的尾巴都以頁為單位 ([Server Arguments](https://docs.sglang.io/docs/advanced_features/server_arguments))。

## 跨請求重用只認滿頁前綴，預設不分使用者

vLLM 不用樹。Automatic Prefix Caching 把已算完的滿塊放進以內容 hash 為鍵的表；新請求從 prompt 起點走同一條 hash chain，就 pin 那些實體塊、跳過對應 prefill。Hash 的元件是 **parent hash、本塊完整的 token ids，以及 extra keys**（LoRA、多模態 hash、多租戶 `cache_salt`、prompt embeds）。文件原句是「We only cache full blocks」。設計頁的例子裡，14 個 token 只對上舊請求的前 10 個、block size 取 4，於是只命中前兩個滿塊共 8 個 token，第三塊差兩個 token 就整塊不算 ([prefix caching design](https://docs.vllm.ai/en/latest/design/prefix_caching.html))。第一塊有一個 token 不同，後面每一塊的 parent hash 都變，整段後綴一起 miss。截至 2026 年 10 月的 `CacheConfig`，**`enable_prefix_caching` 預設 True**，hash 演算法自 v0.11 起預設 `sha256`（先 pickle 再 SHA-256）。CLI 的 `--enable-prefix-caching` 預設印成 `None`，沒指定就沿用 config 的 True，要用 `--no-enable-prefix-caching` 才關 ([CacheConfig](https://docs.vllm.ai/en/latest/api/vllm/config/cache/)；[CLI](https://docs.vllm.ai/en/latest/cli/serve/))。V0「預設關閉」已過時。`xxhash` 被寫明在多租戶環境可能因碰撞造成未定義行為，甚至洩漏私人資訊 ([prefix caching design](https://docs.vllm.ai/en/latest/design/prefix_caching.html))。

查找發生在請求第一次被排程時，對 prompt 的滿塊做 hash。請求變成 running 之後，設計頁只走 `allocate_slots()`，不再呼叫 `get_computed_blocks()`。Chunked prefill 因此不會把已經命中的前綴作廢，但後續 chunk 也不會撿到別的請求在中途新寫入的 hit。同一 batch 裡剛滿的塊會立刻進 cache，供其他請求重用 ([prefix caching design](https://docs.vllm.ai/en/latest/design/prefix_caching.html))。Hybrid 模型的可重用長度是各 KV group hit 的交集。EAGLE 會丟掉最後一個 matched block，讓 drafter 重算最後一段 hidden state；在 hybrid 上這個對齊單位可以遠大於一個小 block ([single_type_kv_cache_manager](https://docs.vllm.ai/en/latest/api/vllm/v1/core/single_type_kv_cache_manager/))。`prompt_logprobs` 或 `skip_reading_prefix_cache` 會跳過讀快取。取樣參數與 grammar 不在設計頁的 hash 元件裡，所以 temperature 本身不會讓相同的 prompt 前綴 miss；它只影響之後生成的 token，以及下一輪把那些 token 接進前綴之後的 hash。v0.31.0 起 extra key 依來源加 tag，block hash 納入 LoRA path，避免同名 adapter 換 path 仍重用舊 KV；同 path 原地改檔仍偵測不到 ([vLLM 0.31.0 notes](https://newreleases.io/project/pypi/vllm/release/0.31.0)；[PR #59335](https://github.com/vllm-project/vllm/pull/59335))。V1 的 block table 是 append-only：同一 hash 可能暫時有兩份滿塊，要等請求釋放才消除，不像 V0 會把新塊改指回舊塊 ([prefix caching design](https://docs.vllm.ai/en/latest/design/prefix_caching.html))。2026-10-14 的 scheduler 原始碼沒有 sequence group，也沒有論文那種 beam search 的 copy-on-write；`SamplingParams.n` 是拆成多個 request 只靠前綴 hash 共享，還是仍在單一請求內做 CoW，這段展開路徑沒有讀完。

SGLang 的重用條件是樹上已有的 token 前綴。`match_prefix` 從 root 依子節點 key 往下走，命中停在節點儲存區段中間就 **split 一次**，讓下一個請求接在精確邊界，而不是複製整段邊。`page_size > 1` 時，共同前綴長度向下對齊到整頁，不滿一頁的尾巴留在 request 上、不進樹 ([radix_cache.py](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/mem_cache/radix_cache.py))。插入時樹持有 pool 的一份引用，與樹重複的 index 會被 `free_segment`。`checkpoint()` 對尚未結束的請求也插入，還可以在 prompt 邊界再切一刀，讓驅逐先丟輸出 KV、留下 prompt。另一個使用者因此不必等這筆請求完全結束，就能命中它已經算出的前綴。多輪對話沒有伺服器端的對話物件：客戶端每一輪都要重送含歷史的完整 prompt，`session_id` 不重建上下文 ([Session-Aware Radix Cache](https://docs.sglang.io/docs/advanced_features/session_radix_cache))。2024 年 DSL 的 `fork` 會先把共享前綴當 hint 送進樹；今日的 HTTP serving 只要完整 token 序列相同就會撞上同一節點，不再靠那個 hint ([Zheng et al.](https://arxiv.org/html/2312.07104v2)；[LMSYS 2024-01-17](https://www.lmsys.org/blog/2024-01-17-sglang/))。

兩邊的排程都預設 **FCFS**，但「不為命中率重排」不等於「不用快取」。vLLM 的 `--scheduling-policy` 預設 `fcfs`，`priority` 是較小的整數先排 ([Engine arguments](https://docs.vllm.ai/en/latest/configuration/engine_args/))。Waiting queue 在 prefix-cache miss 時會 `continue` 而不是 `break`，原始碼註解寫明這並不嚴格遵守 FCFS。SGLang 的 `--schedule-policy` 在 2026-10-14 的文件上也預設 `fcfs`。`fcfs` 仍會 match radix、縮短 prefill，只是不打亂到達順序。論文要的 longest-shared-prefix-first 對應今日的 `lpm`。v0.3.6（2024-11-22）的預設字串還是 `lpm`，後來才改成 `fcfs` ([Server Arguments](https://docs.sglang.io/docs/advanced_features/server_arguments)；[v0.3.6 server_args.py](https://github.com/sgl-project/sglang/blob/v0.3.6/python/sglang/srt/server_args.py))。`lpm` 與 `hrrn` 在 waiting queue 過長時會退回 `fcfs`。同時湧入、而 GPU 樹上還沒有的相同前綴，會先在模擬樹裡比對，只放行其中一筆去把前綴寫進真的樹，其餘暫時降優先 ([schedule_policy.py](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/managers/schedule_policy.py))。`extra_key` 與 `cache_salt` 都空時，子節點 key 只剩 token id，不同使用者的相同前綴就進同一節點。影像會岔開：每個多模態 item 的 hash 變成 pad token 插進序列，`pad_value = 1_000_000 + (hash % 2^30)` ([schedule_batch.py](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/managers/schedule_batch.py))。取樣參數不在 `RadixKey` 的組鍵欄位裡。

可以引用的加速數字高度依賴前綴還放不放得進池。PrefixBench-H100（第三方論文，2026-09）在 **8192-token 共享前綴**上，vLLM 的 p50 TTFT 從無重用的 **345.1 ms** 降到 **53.0 ms**，約 6.5 倍；工作集達到容量 13.2 倍時，vLLM hit rate 掉到 **5.6%**，p50 TTFT 回到約 1.42 秒 ([arXiv:2609.19657](https://arxiv.org/html/2609.19657))。官方 APC 功能頁只說吞吐更高、延遲更低，沒有 hit rate，並寫明不加速 decode ([Automatic Prefix Caching](https://docs.vllm.ai/en/stable/features/automatic_prefix_caching/))。SGLang 2024 年部落格的「up to 5×」與論文摘要的「up to 6.4×」不是同一組實驗，不應混成一個數字 ([LMSYS 2024-01-17](https://www.lmsys.org/blog/2024-01-17-sglang/)；[arXiv:2312.07104v2](https://arxiv.org/html/2312.07104v2))。2026 年 8 月的 unified tree 加上 500 GiB Mooncake L3，DeepSeek-V4-Flash 的有效輸入吞吐（分子含命中前綴）從只有 L1 的 **9.4K** 到 **145.5K tok/s**，hit rate 約 **98%**。這不是純 GPU radix，也不是 decode 生成吞吐 ([Unified Radix Cache](https://www.sglang.io/blog/unified-radix-cache))。vLLM 2026-10-12 部落格的 1.6× 與 3.3× 是關掉本地 prefix cache 之後的雙向 KV 傳輸，不能算成 APC 的收益 ([vLLM blog 2026-10-12](https://vllm.ai/blog/2026-10-12-bidirectional-kvxfer-multiturn-agentic-workload))。

## 沒人握著的前綴先走 LRU，在跑的請求被搶佔後重算

vLLM 把「正在用」和「還能被命中」拆開。**`ref_cnt > 0` 的塊不在 free queue**，正常 LRU 碰不到。`ref_cnt` 降到 0 才進 free queue，但 hash 還在，所以仍是 cached。真正的驅逐發生在分配器從 free queue **頭部**取到一塊仍帶 hash 的塊時：從 hash map 拔掉、清掉 hash，之後不能再 hit。釋放時以反序加到 queue 尾端，因為請求的最後一塊 hash 了更多 token、較不容易被重用，應先被趕走。共享的前段因此比獨特的尾巴活得久 ([prefix caching design](https://docs.vllm.ai/en/latest/design/prefix_caching.html))。這不是第二套政策，是在同一條 LRU 佇列上偏置順序。

這個機制清的是沒人引用的前綴。Running 請求還需要新塊，而 free queue 連可驅逐的 cached 塊都不夠時，`allocate_slots` 回傳失敗，scheduler 改走搶佔。2026 年 10 月 14 日的 `main` 上，FCFS 的受害者是 `running[-1]`；priority 政策則取 priority 值較大、且到達較晚者。`_preempt_request` 釋放該請求的 GPU block，把 `num_computed_tokens` 清零，狀態改成 `PREEMPTED`，再 **prepend** 回 waiting。程式裡沒有把 KV 拷到 CPU swap 的分支 ([scheduler.py](https://github.com/vllm-project/vllm/blob/main/vllm/v1/core/sched/scheduler.py))。調優文件寫明 V1 預設是 **`RECOMPUTE` 而不是 `SWAP`**，因為重算在 V1 架構裡的 overhead 較低 ([Optimization and Tuning](https://docs.vllm.ai/en/latest/configuration/optimization/))。2026-10-14 的 latest engine arguments 頁不再列出 `--preemption-mode` 或 `--swap-space`。論文裡「搶佔後停止收新請求，直到被搶佔者全部跑完」也不再成立：被搶佔者回到 waiting，下一步可以再跟別人搶塊 ([Kwon et al., §4.5](https://arxiv.org/html/2309.06180))。`--watermark` 預設 **0.0**，也就是不預留空塊來防止反覆搶佔。`--scheduler-reserve-full-isl` 預設 True，准入時要求整段 input 放得進 KV，而不是只看第一個 chunk，避免 chunked prefill 過度准入造成 thrashing ([Engine arguments](https://docs.vllm.ai/en/latest/configuration/engine_args/))。設計頁的一般釋放路徑會讓 `ref_cnt` 歸零的滿塊留在 free queue 裡、hash 還在，因此重算量可以小於整段 prompt。搶佔呼叫的是 `_free_request_blocks`，這次沒有逐行確認它與那條路徑相同，所以「被搶佔的滿塊是否一定還能 hit」還沒有原始碼級的保證。

SGLang 的閒置前綴也是從葉往根收。只驅逐「有 KV、`lock_ref` 為 0、沒有仍握有 KV 的子節點」的葉。Root 的 `lock_ref` 固定為 1，不會被當成受害者。請求開始用某段前綴時鎖住該節點與祖先，解鎖要重放同一張 receipt ([Radix Cache Eviction Policies](https://docs.sglang.io/docs/advanced_features/radix_eviction_policy)；[radix_cache.py](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/mem_cache/radix_cache.py))。`--radix-eviction-policy` 預設 **`lru`**。文件還列出 `lfu`、`slru`（`protected_threshold` 預設 2）、`priority`，以及 `tlru`（先丟對話裡下一輪用不到的尾端）。政策只打分、不能 pin：其他人都清掉仍不夠時，分數再高也會被趕走。平手退回 LRU。Server arguments 表的 choices 沒有寫 `tlru`，與 eviction 專頁衝突；這次沒有跑 `--help` 對 CLI parser ([Server Arguments](https://docs.sglang.io/docs/advanced_features/server_arguments)；[eviction policy](https://docs.sglang.io/docs/advanced_features/radix_eviction_policy))。`--enable-session-radix-cache` 加上穩定的 `session_id` 只是軟保護。FULL 槽先趕沒有 session 參考的節點，再趕參考數少的，然後才是 LRU。`/close_session` 只拿掉參考，不立刻釋放。未參考的 KV 清光仍不夠時，被參考的也會走 ([Session-Aware Radix Cache](https://docs.sglang.io/docs/advanced_features/session_radix_cache))。相對「HiRadixCache + LRU」，同一套 session-aware eviction 在 SWE-bench 上把 DeepSeek-V4-Pro 的 TTFT 最多降了 **11.0%**（batch 128，裝置 hit 從 42% 到 51%），把 Qwen3.5-397B-A17B 最多降了 **16.6%**（batch 64） ([Unified Radix Cache](https://www.sglang.io/blog/unified-radix-cache))。

Running decode 放不進池時是另一條路，叫 retract，不是把葉從樹上摘掉。預設先撤回 **已生成 token 較少** 的請求；輸出一樣長時，先撤回原始輸入較長的。`priority` 政策可以把 priority 放在這個排序鍵前面。釋放時 `checkpoint=False`，註解寫明當下需要空間，**不要把這段 KV 插回 radix tree**，接著還會再多趕一段與剩餘請求數成正比的 token。`SGLANG_RETRACT_DECODE_STEPS` 的預設值這次沒讀到。Beam group 不能 retract，直接回 HTTP 500。至少留一個請求；連最後一個都放不下就中止該請求，而不是讓 scheduler 崩潰 ([schedule_batch.py](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/managers/schedule_batch.py))。合一引擎因此是事後重算，而且別的請求也接不上這段剛被撤下的前綴。只有 `disaggregation_mode == "decode"` 且 backup 成功，才把 KV 放到 host，之後 `load_kv_cache` 免重算。Host pool 耗盡則中止請求：host pool 路徑是 HTTP 500，沒有 backup 是 HTTP 503。帶 `input_embeds` 的請求在 retract 時會丟掉已生成的 `output_ids`，整段重跑。這不是 CUDA activation OOM 的解法。Prefill OOM 要降 `--chunked-prefill-size`，decode OOM 要降 `--max-running-requests`，或把 `--mem-fraction-static` 降到 0.8 或 0.7，用較小的池換較少的 OOM 與較低的併發。文件把大約每分鐘一次以內的 retract 視為可接受；經常看到 pool full 的警告時，把 `--schedule-conservativeness` 升到約 1.3 ([hyperparameter tuning](https://docs.sglang.io/docs/advanced_features/hyperparameter_tuning))。

兩套系統都可以把 KV 放到 GPU 以外，但那不是論文裡的 swap preemption。vLLM 的 `--cpu-offload-gb` 卸載的是權重。Prefix KV 的外層是 connector：先查本地 GPU hash，然後才是 CPU、檔案系統或 LMCache，最後才重算。`OffloadingConnector` 與 `SimpleCPUOffloadConnector` 都要求 prefix caching 開著，因為它們靠 block hash 知道要搬哪一塊 ([simple_cpu_offload_connector](https://docs.vllm.ai/en/latest/api/vllm/distributed/kv_transfer/kv_connector/v1/simple_cpu_offload_connector/)；[KV offloading guide v0.24](https://docs.vllm.ai/en/v0.24.0/features/kv_offloading_usage/))。SGLang 的 HiCache 預設關閉（`--enable-hierarchical-cache` 為 False）。打開之後是同一棵樹的三層：L1 GPU 與 L2 host 都是該 instance 私有，連同一台機器上的兩個進程也不互讀 L2；L3 只有 backend 指向同一 namespace 才跨 instance。`--hicache-ratio` 預設 **2.0**，寫入預設 `write_through`，L3 prefetch 預設要超過 **256 tokens** ([HiCache design](https://docs.sglang.io/docs/advanced_features/hicache_design)；[Server Arguments](https://docs.sglang.io/docs/advanced_features/server_arguments))。Retract 不會自動把運行中的 KV 塞進 HiCache。L2 只有在原本的 write-back，或 decode 側的 backup 已經寫下去時，才接得住。`HiRadixCache` 自 v0.5.19 起由 `UnifiedRadixCache` 承接，2026-09-22 的 PR #40787 以「已無呼叫者」刪除該類別 ([PR #40787](https://github.com/sgl-project/sglang/pull/40787))。

## Salt 切斷命中，卻不把顯存切成租戶配額

預設沒有租戶邊界。vLLM 安全文件寫：prefix caching 會重用共享 prompt 前綴的 KV block，在多租戶部署裡這是時序側信道 **CVE-2025-46570**。攻擊者用 TTFT 的差判斷猜的前綴是否已在別人的快取裡。被引用的研究顯示，前綴只有 **8 tokens** 時幾乎可完美區分，ROC AUC **0.99** ([Security, v0.31.0](https://docs.vllm.ai/en/v0.31.0/usage/security/)；[GHSA-4qjh-9fv9-r85r](https://github.com/vllm-project/vllm/security/advisories/GHSA-4qjh-9fv9-r85r)；[Leaking Secrets from Prefix Caches](https://arxiv.org/html/2411.18191v1))。隔離方式是每個請求帶一個秘密 `cache_salt`，混進 **第一個** KV block 的 hash，之後整條 chain 都不同，只有相同 salt 能共享。它不是加密，也不把別的租戶的 KV 從 GPU 抹掉。同一進程裡，不同 salt 的塊仍佔同一池，只是不能互相 hit。可猜到的 salt（使用者名稱、帳號 ID）擋不住會猜 salt 的人。文件舉例用約 43 個 base64 字元、256 bits 的亂數，粒度可以是 per-user 或 per-group。不傳 salt 等於全部請求可互享，只適合單租戶，或在乎命中率多於前綴隱私 ([Security](https://docs.vllm.ai/en/v0.31.0/usage/security/))。多模態 part 的 client `uuid` 若衝突，會讓不同媒體共用快取身份；`cache_salt` 是額外防線，但預設不傳。沒有文件化的 per-user KV 配額。`max_num_seqs`、`max_num_batched_tokens`、watermark、`scheduler_reserve_full_isl` 都是全域閥。一個很長的請求可以經由 FCFS 或 priority 搶佔，把別的使用者擠去重算。Data parallelism 是把整個模型複製到另一組 GPU、各有各的池，不是在同一池裡切配額 ([Optimization and Tuning](https://docs.vllm.ai/en/latest/configuration/optimization/))。

SGLang 同樣沒有把 API key 自動做成 namespace。`match_prefix` 寫明：不同 `extra_key` 即使 token 相同也不共享節點，用途包含 LoRA，以及呼叫端故意不共享的 sampling salt、cache version 與 retrieval context。`cache_salt` 另進 `RadixKey`。註解說它同時 namespace 樹、storage 與 KV events；`extra_key` namespace 樹與 storage，但不進 KV events ([radix_cache.py](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/mem_cache/radix_cache.py))。`session_id` 不是這把鑰匙。它只登記可重用 leaf 的軟參考，不阻止別人 match 同一條 token 路徑。LoRA 的 `lora_id` 被拼進 `extra_key`。2026-10-14 的 `Req.__init__` 仍是 `(extra_key or "") + lora_id`，而 issue #24638 已證明呼叫者自填的 `extra_key` 可以冒充某個 `lora_id`，讓 base 模型讀到 LoRA 算出的 KV ([schedule_batch.py](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/managers/schedule_batch.py)；[issue #24638](https://github.com/sgl-project/sglang/issues/24638))。KVGov（2026-08）把未加鹽的 vLLM 與 SGLang 一起當成攻擊面：PROMPTPEEK 在 SGLang radix tree 上的攻擊成功率寫成 **99–100%**，訊號是 TTFT 與 matched prefix 長度，比 vLLM 的 block 量化更細。作者提案是每個 principal 一棵不相交的樹，那不是 SGLang 已合併的功能 ([arXiv:2608.09225](https://arxiv.org/pdf/2608.09225v1))。L1 與 L2 不跨 instance，所以「一租戶一進程」自然不共享 host KV；許多租戶打進同一個 server 進程則共享該樹。L3 在同一 backend namespace 裡還會跨 instance 共享，因此 salt 必須進儲存鍵，否則隔離只存在於單機記憶體 ([HiCache design](https://docs.sglang.io/docs/advanced_features/hicache_design))。2026 年 5 月的 issue #24568 曾顯示對外的 block hash 漏掉 salt。10 月的 `RadixKey` 註解把 `cache_salt` 寫進 KV events，但這次沒有用一筆 event payload 再驗證；`extra_key` 的註解則仍說它不進 event ([issue #24568](https://github.com/sgl-project/sglang/issues/24568))。

## 2026 年 10 月的預設已經離開兩篇早期論文

兩篇論文的不變量還在，預設配置已經不是論文裡的那套。PagedAttention 仍是固定大小的實體塊加上 per-request block table。RadixAttention 仍是 CPU 上的樹、GPU 上的 paged KV、最長前綴 match、中段 split，以及用引用計數擋住 running 路徑的驅逐。不能沿用的是：vLLM 還有與 GPU 等量的 CPU block allocator，以及 beam search 的 copy-on-write；SGLang 預設會為了 hit rate 重排；以及「沒有命名空間，所以所有使用者必然共享，也沒有別的開關」。

| 面向 | 早期論文裡的設計 | 2026 年 10 月的實作 |
| --- | --- | --- |
| vLLM 引擎 | 集中式 block manager，GPU workers 共用 logical 到 physical 的對照 ([論文 §4.6](https://arxiv.org/html/2309.06180)) | V0 已在 v0.11.0 刪除，V1 是唯一引擎。類別是 `KVCacheManager` 加 `BlockPool`，不是 `BlockSpaceManager` ([v0.11.0](https://github.com/vllm-project/vllm/releases/tag/v0.11.0)) |
| 跨請求前綴 | 論文沒有 automatic prefix caching。共享靠 parallel sampling 與 beam 的 reference count，以及 copy-on-write ([§4.4](https://arxiv.org/html/2309.06180)) | APC 在 V1 預設開，鍵是 hash chain，只快取滿塊。2026-10-14 的 scheduler 原始碼沒有 sequence group，也沒有 beam 的 fork/CoW 路徑 ([設計頁](https://docs.vllm.ai/en/latest/design/prefix_caching.html)；[scheduler.py](https://github.com/vllm-project/vllm/blob/main/vllm/v1/core/sched/scheduler.py)) |
| 記憶體耗盡 | Swap 到 CPU，或重算；單序列傾向重算。搶佔後停止收新請求。CPU swap 的塊數不超過 GPU 塊數 ([§4.5](https://arxiv.org/html/2309.06180)) | 預設只重算：釋放 GPU block、`num_computed_tokens = 0`、放回 waiting。沒有 swap 分支。Latest 參數頁不再列 `--preemption-mode` 與 `--swap-space` ([scheduler.py](https://github.com/vllm-project/vllm/blob/main/vllm/v1/core/sched/scheduler.py)；[調優文件](https://docs.vllm.ai/en/latest/configuration/optimization/)) |
| SGLang 排程 | Longest-shared-prefix-first。離線且容量夠時，等價於在請求的 radix tree 上做 DFS ([Theorem 3.1](https://arxiv.org/html/2312.07104v2)) | 文件預設 `fcfs`。`lpm` 與 `dfs-weight` 仍可選。v0.3.6 的預設還是 `lpm` ([Server Arguments](https://docs.sglang.io/docs/advanced_features/server_arguments)；[v0.3.6](https://github.com/sgl-project/sglang/blob/v0.3.6/python/sglang/srt/server_args.py)) |
| SGLang 的頁與池 | 每頁等於一個 token。沒有另劃固定 cache pool，必要時把已快取的 token 全部讓給 batch ([論文](https://arxiv.org/html/2312.07104v2)) | `--page-size` 預設仍是 1，但可以大於 1，而且只快取整頁。池由 `mem_fraction_static` 事先劃定，驅逐是把葉的 index 還給 allocator ([Server Arguments](https://docs.sglang.io/docs/advanced_features/server_arguments)) |
| SGLang 的驅逐與命名空間 | 只有 LRU。沒有 per-request namespace。`fork` 要前端先送 hint ([論文](https://arxiv.org/html/2312.07104v2)) | 預設仍是 LRU，另有 `lfu`、`slru`、`priority`、`tlru`。`extra_key` 與 `cache_salt` 把相同 token 拆成不相交的子樹。預設樹是 `UnifiedRadixCache`。Session 參考是軟保護。HTTP 路徑靠完整 prompt，不靠 DSL hint ([eviction policy](https://docs.sglang.io/docs/advanced_features/radix_eviction_policy)；[registry.py](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/mem_cache/registry.py)) |

論文把重算選成預設的理由，仍然對得上後來的架構選擇。2023 年的消融裡，小 block 的 swapping 吃不滿 PCIe，recomputation 的 overhead 跨 block size 大致持平，而且「never higher than 20% of swapping’s latency」 ([Kwon et al., §7.3](https://arxiv.org/html/2309.06180))。這個 20% 是當時的 swapping 對重算，不能套到 2026 年的 `OffloadingConnector` 或 HiCache。V0 在多 sequence（例如 beam）時仍改走 SWAP，因為重算當時不支援多 sequence；那條分支隨 V0 一起退出 ([vllm.core.scheduler](https://docs.vllm.ai/api/vllm/core/scheduler.html))。Stable 指南還寫可以用 `VLLM_USE_V1=0` 關掉 V1，這與 v0.11.0「V0 程式已刪除」、其後發到 v0.31.0 的 release note 衝突。2026 年 10 月應以 V1 為唯一引擎 ([V1 guide](https://docs.vllm.ai/en/stable/usage/v1_guide.html)；[v0.11.0](https://github.com/vllm-project/vllm/releases/tag/v0.11.0))。

SGLang 這邊，想回到論文的排程要顯式加上 `--schedule-policy lpm`。只開預設的 `fcfs` 仍有 radix reuse。多輪在記憶體壓力下想少被別人擠掉，現行旗標是 `--enable-session-radix-cache`，不是一個 2024 年的 pin API。Rust tree core 在 PR #29074 自述不是預設路徑。部落格裡的 SWA TTFT 降幅，正文是 38%、開頭又寫 42%，都出自同一篇，實驗設定沒有在這裡對帳，不應寫成預設部署的收益 ([PR #29074](https://github.com/sgl-project/sglang/pull/29074)；[Unified Radix Cache](https://www.sglang.io/blog/unified-radix-cache))。2025 年 9 月 HiCache 文的「up to 6× throughput、up to 80% TTFT」是作者對 host 加 L3 的摘要，不是 2024 年 in-GPU radix 的數字 ([LMSYS 2025-09-10](https://www.lmsys.org/blog/2025-09-10-sglang-hicache/))。

## Conclusion

兩套系統用來同時服務多人的合約已經收斂，資料結構沒有。合約是一個進程、一塊開機時劃好的 GPU 池、請求在同一次 forward 裡交錯、相同前綴預設互相借用。公平與隔離都不是這份合約的內建性質。結構差會表現在命中粒度上：vLLM 差一個 token 就從該塊起到後綴全 miss，不滿的尾巴也永遠不能給下一筆用；SGLang 在 `page_size == 1` 時可以在任意 token 邊界 split，頁放大之後才退回「只認整頁」。KVGov 把較細的樹當成較細的時序訊號，不是較安全的預設。

因此 2026 年 10 月的操作手冊與論文相反。照 2024 年的 SGLang 去追命中率，會以為預設排程仍是 longest-prefix，實際上要自己打開 `lpm`，否則共享長 system prompt 的人不會插隊，只是前綴還在時少算一段 prefill。照 2023 年的 vLLM 去準備 OOM，會配置與 GPU 等量的 CPU swap，實際上預設是把 running 請求的塊丟掉再重算，CPU 上的 KV 是另外接上的 connector。照 `session_id`、API key 或使用者名稱去隔租戶，兩邊都會繼續共享私有前綴。Salt 必須是秘密、必須每筆請求都帶，在 SGLang 上還要確認它進了 L3 與對外 event 的鍵。Salt 加上之後，命中率只存在於同一個 principal 內部，池卻仍然是大家一起用的。長而獨特的對話尾巴先被 LRU 或 retract 犧牲，共享的前段則由所有沒加鹽的人共同養著。公平與隱私都要另外付錢，快取管理本身不附贈。
