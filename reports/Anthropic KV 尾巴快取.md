# 斷點前移並非獨立尾巴快取

Anthropic 到 2026 年 10 月沒有名為 tail cache、suffix cache、ephemeral tail 或尾巴快取的產品。用來同時服務多個請求與使用者的公開合約是 prompt caching：把依序排成 `tools`、`system`、`messages` 的前綴，在 `cache_control` 斷點處做成 cryptographic hash，把對應的 KV 留在記憶體裡，讓隔離邊界內、模型相同、到該斷點為止位元組完全相同的後續請求改付 cache read、少做 prefill。Claude API、Claude Platform on AWS 與 Microsoft Foundry 的邊界是 **workspace**，不是 API key，也不是終端使用者；Amazon Bedrock 與 Google Cloud 在 Anthropic 文件裡是 **organization**，但 Vertex 自己寫 Google Cloud project、AWS 產品頁寫 account，三個詞沒有被對成同一個 ID。使用者印象裡負責管理命中的「尾巴」，最接近的官方機制是 automatic caching 把斷點推到最後一個可快取 block、explicit breakpoint 的 incremental caching，以及從斷點往回最多 **20 個 position** 去找先前寫過的前綴；AWS 中文部落格的 moving tail checkpoint、社群說的動態後綴，以及 Claude Code 功能請求裡的 `messagesTail`，都是對這個寫入點的暱稱。命中的永遠是斷點為止的整段前綴。斷點後面每輪都變的後綴只進 `input_tokens`，前綴一改就無法單獨把對話末端撿回來。

## 同一個 workspace 裡，相同前綴互相省下 prefill

第一方沒有公開 GPU 頁池、radix tree、block 大小或跨 replica 的槽位。公開的多租戶管理是一組記憶體中的前綴條目，加上誰可以讀它們。快取鍵是「到 cache control point 為止的 prompt」的 cryptographic hash，所以只有到斷點為止完全相同的請求能進同一筆；命中還要求 **100% 相同的文字與圖片**，cache diagnostics 與中途 system 訊息頁把它寫成 byte-for-byte（[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)；[Cache diagnostics](https://platform.claude.com/docs/en/build-with-claude/cache-diagnostics)）。模型是另一個命名空間。Diagnostics 的 `model_changed` 寫明 cache 依模型分開，2026-09-08 的平台文章則說 prompt cache 被釘在特定模型上，子代理與分支只有在前綴 byte-identical、同一模型、同一 effort 時才共享父對話的 cache（[Cache diagnostics](https://platform.claude.com/docs/en/build-with-claude/cache-diagnostics)；[Reducing cost and improving performance](https://claude.com/resources/articles/reducing-cost-and-improving-performance-with-claude-platform)）。

隔離不是全域，也沒有寫成 per end user 或 per API key。2026-10-14 的英文頁寫：組織之間永不共享，就算 prompt 一字不差；Claude API、Claude Platform on AWS、Microsoft Foundry 在組織之內再按 workspace 切開，Bedrock 與 Google Cloud 則只有 organization 級（[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)；[Workspaces](https://platform.claude.com/docs/en/manage-claude/workspaces)）。API key 被綁在 workspace 上，文件沒有第二層 per-key 隔離，因此同一 workspace 裡不同 key、不同終端使用者，只要前綴 hash 與會被畫進 prompt 的參數一致，就可以互打。這是從「隔離單位是 workspace」推出的，沒有一句原文寫「兩把 key 共享同一筆」。跨 workspace 的 key 若能選 workspace，合理預期打到的是該次請求所屬 workspace 的池；文件同樣沒有單獨寫這條路由。法文頁把 workspace 隔離記成 **2026 年 2 月 5 日**起，當天的英文 release notes 卻只有 Opus 4.6、effort、compaction 與 data residency，沒有 cache isolation，英文現頁的警告框也不附日期，所以生效日與舊組織級條目何時清空都不能當成已核對事實（[法文 Prompt caching](https://platform.claude.com/docs/fr/build-with-claude/prompt-caching)；[Release notes](https://platform.claude.com/docs/en/release-notes/overview)）。2025-02-25 的 Wayback 與仍留在 `docs.claude.com` 的殘頁只寫組織級，同一組織內的使用者可以互打；那份殘頁不能拿來描述 2026 年 10 月的 Claude API（[Wayback 2025-02-25](https://web.archive.org/web/20250225142138/https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching)；[docs.claude.com 殘頁](https://docs.claude.com/en/docs/build-with-claude/prompt-caching)）。

平台用詞比 Anthropic 的句子更細，而且互相衝突。Vertex 頁（標 2026-10-13）寫 cache 屬於 **Google Cloud project**，別的 project 不能用；Google 把 hash 當 User Metadata／Service Data，不當 Cloud DPA 下的 Customer Data（[Vertex prompt caching](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/partner-models/claude/prompt-caching)）。AWS 產品頁寫 cache 專屬於 **account**，內容是代表 prompt 的內部模型狀態（[Amazon Bedrock prompt caching](https://aws.amazon.com/bedrock/prompt-caching/)）。在這兩個平台上不能假設 Anthropic workspace 仍是邊界，也不能把「account」「project」「organization」當成同一個 ID。一個 GCP organization 若有多個 project，照 Vertex 頁會少估共享、多估隔離。Bedrock 的 implicit cache 與 explicit cache 是否同一隔離域，user guide 沒有寫。

費用與延遲的轉移只發生在這條邊界內，而且讀取者必須自己參加 caching。找到條目就用快取版，少做處理、少付 input；找不到就處理整段 prompt，並在 **回應開始之後** 才把前綴寫進去。並行請求要等第一個 response 開始，後面的請求才 hit 得到。Message Batches 因為順序不定，命中被明文寫成 best-effort（[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)）。寫入者付溢價，讀取者付自己的 read，輸出分布不變：prompt caching 不影響 output token 的生成。5 分鐘 write 是 base input 的 **1.25 倍**，1 小時 write 是 **2 倍**；read 一般是 **0.1 倍**，Opus 5.5 與 Sonnet 5.5 是 **0.05 倍**，Fable 5.1 與 Mythos 5.1 是 **0.025 倍**。2026-10-07 把 Sonnet 5.5 的 read 從每百萬 token **$0.20** 降到 **$0.10**；2026-09-01 把 Fable 5.1 與 Mythos 5.1 的 read 定在 **$0.25**。Opus 5.5 的錨點是 base input **$4**、5 分鐘 write **$5**、1 小時 write **$8**、hit **$0.20**（[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)；[Release notes，2026-10-07](https://platform.claude.com/docs/en/release-notes/overview)）。Rate limits 頁仍有一句「一律 10%」，與這張表衝突，計價應以 prompt caching 表為準。多數模型的 cache read 不計入 ITPM，Haiku 3.5 是例外。Priority Tier 把 read 權重算成 0.1、5 分鐘 write 算成 1.25、1 小時 write 算成 2.00，那是容量折算，不是 5.5／5.1 的帳單單價（[Rate limits](https://platform.claude.com/docs/en/api/rate-limits)；[Service tiers](https://platform.claude.com/docs/en/api/service-tiers)）。沒有句子說讀取者的 hit 記到寫入者的帳單上。

保留合約是最短存活，不是 LRU，也沒有公開容量上限。預設至少 **5 分鐘**，`{"type": "ephemeral", "ttl": "1h"}` 至少 **1 小時**；`ephemeral` 是唯一的 cache type。計時從寫入或讀取該條目的請求開始，不是從回應結束開始。串流 4 分鐘時，5 分鐘條目只剩約 1 分鐘給下一筆。每次使用以免費刷新重算 TTL，不是再付一次 write。過期後「迅速但非立即」刪除，沒有手動清除，也沒有秒數上界，所以不能假設過期後仍 hit 得到（[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)）。範例註解裡的 evict 指的是閒置超過 TTL。容量壓力能否提前趕走條目，文件沉默；把「最小 TTL」讀成「記憶體不夠仍保證活滿」超出原文。兩種 TTL 的延遲表現相同，換的是存活與 write 單價。流量比 5 分鐘更密就繼續用 5 分鐘，因為 hit 會免費續期；1 小時適合間隔落在 5 分鐘與 1 小時之間、在意延遲，或想用「cache hit 不扣 rate limit」。較長 TTL 的斷點必須出現在較短 TTL 之前。Prompt caching（automatic 與 explicit）是 ZDR eligible：不存 prompt 與回應原文，KV 與 hash 只在記憶體、不落盤，活滿最小 TTL 後刪除，而且仍沿用上述隔離。ZDR 沒有關掉共享。Fable 5.1 與 Mythos 5.1 另有模型級限制，要求 30 天資料保留，除非另行授權否則不在 ZDR 下提供；那不是 cache 功能本身的例外（[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)；[Release notes，2026-09-01](https://platform.claude.com/docs/en/release-notes/overview)）。舊的 Zero Data Retention 專頁仍把這項稱為 beta、並寫 5 或 60 分鐘與組織隔離，用詞舊於現頁，以 prompt caching 頁為準。

Claude Code 部落格裡的 “globally cached” 是 harness 把靜態 system prompt 與工具放在最前面的分段標籤，不是全體 API 客戶共用一塊 KV。同文的條件仍是前綴匹配（[Lessons from building Claude Code](https://claude.com/blog/lessons-from-building-claude-code-prompt-caching-is-everything)）。

## 「尾巴快取」是斷點被推到最後一塊的暱稱

官方只有兩種啟用方式，而且都是 opt-in。頂層放一個 `cache_control`，系統把斷點放到最後一個可快取 block，並隨對話成長往前移，這叫 automatic caching。或者把 `cache_control` 直接放在 content block 上，最多 **4 個** explicit breakpoint；頂層那一格佔用四個名額之一。沒有任何 `cache_control` 時，Claude API 什麼都不快取，每筆請求付全額 input。第五個 explicit breakpoint 回 400；最後一塊已有相同 TTL 的 explicit 標記時，automatic 是 no-op；TTL 不同回 400；最後一塊不合格就默默往前找，找不到就跳過快取。Automatic caching 在 2026-02-19 上線，2026-10-14 的文件寫成除了 legacy Amazon Bedrock（Opus 4.6 與更早）以外的平台都可用；那個 legacy 整合對頂層欄位回 **400**，必須改放 explicit breakpoint（[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)；[Release notes，2026-02-19](https://platform.claude.com/docs/en/release-notes/overview)；[Mid-conversation system messages](https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages)）。

被寫進去的單位始終是從 prompt 開頭到斷點的整段前綴，不是末端片段。標記一個 block 只寫恰好一筆：該 block 結尾處的 prefix hash。系統不會為更早的位置各寫一筆。多輪官方做法是快取「到目前為止的穩定前綴」。Explicit 範例把每一輪最後一則訊息的最後一個 block 標上 `cache_control`，使對話被 incrementally cached；先前輪次之後不必再標，只要還在 TTL 內，lookback 仍把那些舊寫入當成 hit，並順便刷新。Automatic 的多輪表更直白：第一筆把斷點放在當時最後一個 user block 並整段寫入，下一筆讀到那個 user、只寫新的 assistant 與 user，再下一筆重複。「The cache breakpoint automatically moves to the last cacheable block」是官方句子，不是社群引申（[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)）。四個斷點的教學順序就是更新頻率：工具陣列的最後一個定義、很少變的 system instructions、RAG 文件、最後一則 user message。只把第四個斷點移到新的最後一則時，前三段 read，新的 user 與上一則 assistant write。

這就是「尾巴」。它是同一條 prefix chain 上最新的寫入點。文件裡和末端有關的官方用詞是 varying suffix、last cacheable block、incremental caching 與 lookback，沒有第二個 cache tier。

| 用語 | 誰在用 | 實際指什麼 |
| --- | --- | --- |
| prompt caching、`cache_control`、automatic caching、lookback、incremental caching | Anthropic 文件 | 唯一的官方機制：在前綴斷點寫入與回讀 |
| moving tail checkpoint、單尾部 checkpoint、當前請求尾部 moving checkpoint | AWS 中國部落格，談 Bedrock | 呼叫端清掉舊 cachePoint，把新的放在當前最後一個 user message 或 toolResult。穩健預設是 system 末尾、tools 末尾，再加這個移動點 |
| 動態後綴、緩存斷點隨著對話增長自動推進 | 知乎 | 使用者訊息、助手回應、工具輸出，以及 automatic caching 的行為 |
| 長尾部、append-only 段 | V2EX 貼文 | 作者自己把歷史訊息分段，不是 API 欄位 |
| `"at": "messagesTail"` | Claude Code issue #58103 | 功能請求裡的假想鍵。作者明說 breakpoint 放置不透明，`cachingPolicy` 並不存在 |
| tail rent | 2026-10-13 的 Medium 文 | 長 session 每一輪重送成長中的對話、即使 cache read 仍累積的費用，不是一種 cache |

這些暱稱的來源分別是 [AWS 中國部落格](https://aws.amazon.com/cn/blogs/china/amazon-bedrock-claude-application-design-prompt-cache-policy/)、[知乎](https://zhuanlan.zhihu.com/p/2017269864117609145)、[V2EX](https://www.v2ex.com/t/1212780)、[issue #58103](https://github.com/anthropics/claude-code/issues/58103) 與 [Where the Tokens Actually Go](https://pub.towardsai.net/where-the-tokens-actually-go-cache-rent-effort-levels-and-routing-in-a-long-claude-code-session-4d1d2a1625df)。沒有搜到 Anthropic 員工把內部 scheduler 叫做 tail cache 或 suffix cache。Code w/ Claude 2026 的 caching 場次沒有公開逐字稿，口語用詞無法核對。

官方自己標出了最容易和這個暱稱搞混的陷阱。有 varying suffix（timestamp、本次使用者原文、每請求上下文）時，斷點要放在靜態前綴的最後一塊，不能放在會變的那一塊上。Lookback 不會去找斷點後面的穩定內容。Automatic caching 把斷點放在最後一個可快取 block，若那一塊每筆都變，就會每次 write、永不 read（[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)）。想命中「到上一輪為止的整段對話」，本輪必須在「下一輪仍會原樣重送」的最後一個 block 上留下寫入。成長中的對話把斷點放在該請求最後一個 block 即可，前提是每一輪新增少於 20 個 position。不想把本輪使用者文字寫進 cache 時，不該用「永遠標在最後一塊」的 automatic caching。

伺服器在呼叫端已經啟用 caching 之後，還會做兩件容易被說成「自動尾巴」的事，兩者仍是前綴斷點。第一件是 lookback，屬讀取側，不是自動為每個 block 寫入。第二件是 server tool：請求已有 prompt caching，且模型用了 web search、web fetch 或 code execution 時，API 在進入 agentic loop 的下一輪之前，自動在 server tool result 上放一個斷點。這個自動斷點一律是預設 **5 分鐘** TTL，與呼叫端的 1 小時無關，所以全用 `ttl: "1h"` 時 usage 仍可能出現 `ephemeral_5m_input_tokens`。完全沒有 `cache_control` 就不會加。它是否佔用四個 breakpoint 名額，工具頁沒有寫（[Tool use with prompt caching](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-use-with-prompt-caching)）。Bedrock 另有一套不放 marker 的 implicit caching，對合格前綴做 best-effort 重用，相同 prompt 不保證 hit；Anthropic 模型在 Bedrock 同時支援 implicit 與 explicit。這不是 Claude API 的 automatic caching，也不是尾巴產品。Vertex 寫的「後續請求含相同文字、圖片與 `cache_control` 就自動命中」指的是已經放了標記之後的 hit（[Bedrock prompt caching](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)；[Vertex prompt caching](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/partner-models/claude/prompt-caching)）。

Claude Code 是客戶端在放 `cache_control`，不是伺服器在前綴改變後仍命中一段 session tail。它預設自己處理 caching，重送 system prompt、專案上下文、先前訊息與工具結果，新內容接在末端。文件寫明 API 比對的是請求開頭，匹配是 exact，前綴任一處改變就重算其後全部，沒有 per-file 或 per-segment caching。正常一輪的前綴就是上一個完整請求，只有最新一輪是新的。層級由穩到變：system prompt（核心指示與工具定義）、project context（CLAUDE.md、auto memory、未限定範圍的規則）、conversation。改對話層仍可命中前兩層；改 system prompt 則全部重算。它會在對話中途附加 file-change notice 這類 system context 並標記該 block；設 `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS` 則該 block 不快取。Gateway 若回 400 並點名 `cache_control`，客戶端會重送，把標記從該 block 挪到最後一則對話訊息，並在之後保持這個位置。對話仍快取，被挪走的 block 以未快取 input 計費。這是文件裡最明確的「尾端 breakpoint」行為，而且只在 gateway 拒絕原本標記時發生。Advisor 工具是例外：定義放在斷點之後，所以開關 `/advisor` 不會拆掉已快取前綴。因此 Claude Code 的主斷點並不是永遠黏在整個請求的絕對最後一個位元組。公開文件沒有列出預設四個斷點各自落在哪個 block，不能斷言每一輪都標在最後一則 user 或 assistant 上（[How Claude Code uses prompt caching](https://code.claude.com/docs/en/prompt-caching)）。

TTL 由客戶端分桶，不是另一套隔離。主對話用 `promptCacheTtl` 或 `CLAUDE_CODE_PROMPT_CACHE_TTL`（`5m` 或 `1h`），其餘用 subagent 的對應設定。未自訂時，訂閱方案內用量的主對話要 1 小時；超出後改扣 usage credits 則降為 5 分鐘。API key 預設主對話 5 分鐘。Subagent 有自己的 system prompt 與工具集，第一個請求讀不到 parent cache。Agent SDK 沒有獨立的 tail-cache API，文件把它指回同一套 token 與 TTL 設定（[How Claude Code uses prompt caching](https://code.claude.com/docs/en/prompt-caching)）。

## 離上一次寫入超過二十個 position，整段前綴就 miss

讀取先算斷點處的 prefix hash。沒有條目就逐 block 往回找先前請求已經寫過的位置，不是找「看起來穩定」的內容。視窗最多 **20 個 position**，斷點自己算第一個。窗內沒有就停，或改從下一個 explicit breakpoint 再查。Lookback 只能找到更早的 breakpoint 寫過的 hash。2025-01-15 起，設一個斷點會自動讀最長的先前已快取前綴，不再要求讀寫標在同一個 block 上；2025-02 的 Wayback 還寫著舊規則（[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)；[Release notes，2025-01-15](https://platform.claude.com/docs/en/release-notes/overview)）。

教學例把這條規則算清楚。第一輪在 block 10 寫入。第二輪斷點在 block 15，往回找到 block 10，只重算 11–15，並在 15 寫新條目。第三輪斷點在 block 35，只查 35 到 16 這 20 個 position，block 15 在窗外，整段 miss。要在 block 15 再放一個斷點，才會開第二個視窗。官方的操作句是：成長中的對話若每一輪新增少於 20 個 block，末端那一個斷點就夠，因為較早的內容不變，下一筆的 lookback 找得到上一筆寫入；一旦把斷點推到離上一次寫入 **20 個以上** 的 block，就要事先在較近的位置再放一個斷點，讓寫入先在那裡累積（[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)）。Claude API 上，連續的 `tool_use` 算一個 position，連續的 `tool_result` 也算一個，所以單輪大量平行工具呼叫不會單靠 block 數量把上一筆寫入擠出視窗。Bedrock 的 simplified cache management 寫的是往回看大約 20 個 content block，用詞是 approximately，沒有證實它也把連續 tool block 折成一個 position（[Bedrock prompt caching](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)）。官方沒有說明 system 與 tools 的 block 是否與 messages 用同一套 position 計數。

計費把「舊前綴」和「這一輪新長出來的尾巴」拆開，但尾巴若在斷點之前，它是新的 prefix write，不是獨立索引。`cache_read_input_tokens` 是斷點之前已快取的 token，`cache_creation_input_tokens` 是這次寫入的 token，`input_tokens` 只計最後一個斷點之後、不進 cache 的 token。三者相加是 total input，而且三段都佔 context window；caching 改的是價格，不是是否佔視窗。低於模型最小長度時兩個 cache 欄位都是 0，請求仍成功、不報錯。沒有名為 cache miss 的 usage 欄位。沒放標記或不夠長時，token 整段落在 `input_tokens`。有斷點、長度夠、hash 不合時，是 write（creation 大於 0、read 為 0），不是免費的 miss。Lookback 命中較早的條目時，同一回應會同時有 read 與 write：read 是到上一輪為止，creation 是新的 assistant 與 user turn，最後一個斷點之後的新 user 文字若沒被標進去，`input_tokens` 會很小（[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)；[Context windows](https://platform.claude.com/docs/en/build-with-claude/context-windows)）。1 小時與 5 分鐘混用時，計費位置是：`A` 為最高 cache hit 的 token 數，`B` 為 `A` 之後最高的 1 小時斷點，`C` 為最後一個斷點；收費是 `A` 的 read、`B - A` 的 1 小時 write、`C - B` 的 5 分鐘 write。讀取一筆 1 小時條目時，剩餘 TTL 會不會被一次 5 分鐘 read 改寫，主文沒有單獨句子，不能記成事實。

最小長度按模型，不按 Haiku／Sonnet／Opus 家族一刀切。現行 Claude API、Claude Platform on AWS、Google Cloud 與 Microsoft Foundry：Fable 5.1、Mythos 5.1、Opus 5.5、Opus 5、Sonnet 5.5、Fable 5、Mythos 5、Haiku 5.5 為 **512**；Mythos Preview 與 Opus 4.7 為 **2,048**；Opus 4.6 與 Opus 4.5 為 **4,096**；Opus 4.8、Sonnet 5、Sonnet 4.6、Sonnet 4.5 等為 **1,024**；Haiku 4.5 為 **4,096**；Haiku 3.5 為 **2,048**。Anthropic 寫這些下限適用於該模型所在的每個平台，同段又說 Bedrock 改看 AWS。Bedrock explicit 表把 Opus 4.7 列成 **4,096**，與 2,048 衝突，在 Bedrock 上應先信 AWS 表。Checkpoint 之間沒有額外的最小 token 數；不夠長的是到該 checkpoint 為止的整個前綴。Bedrock 不夠長時推論仍成功，只是前綴沒被寫入（[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)；[Bedrock prompt caching](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)）。

靜態前綴可以在使用者流量之前先寫一筆。`max_tokens: 0` 會把 prompt 讀進模型、在斷點寫 cache、不生成輸出，output token 計費為 0，`stop_reason` 為 `max_tokens`。斷點要放在與正式請求共用的最後一塊，通常是 system 或 tools，不能放在 placeholder user message 上，否則條目被釘在那個 placeholder。Thinking 與 `output_config.effort` 必須與正式流量相同。5 分鐘快取至少要每 5 分鐘再預熱一次。`max_tokens: 0` 在串流、extended thinking、structured outputs、`tool_choice` 為 `tool` 或 `any`，以及 Message Batches 裡會被拒。文件說這取代了過去 `max_tokens: 1` 的暖機做法（[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)）。

2024 年的延遲數字不能當成這套 lookback 在 2026 年的 SLA。部落格寫長 prompt 成本最多降 **90%**、延遲最多降 **85%**，10 萬 token 的書從 TTFT **11.5 秒**降到 **2.4 秒**；2024-12-17 的 release notes 寫的是延遲最多 **80%**。兩個 “up to” 沒有對齊，現行文件只說一般會看到較好的 time-to-first-token。沒有公布的服務級 hit rate。Claude Code 對 hit rate 做告警，甚至低到會宣 SEV，但沒有給百分比。次級文章裡的 92% 不是 Anthropic 的數字（[Prompt caching with Claude](https://claude.com/blog/prompt-caching)；[Release notes，2024-12-17](https://platform.claude.com/docs/en/release-notes/overview)；[Lessons from building Claude Code](https://claude.com/blog/lessons-from-building-claude-code-prompt-caching-is-everything)）。

## 從改動點往後全數重算，末端不能單獨命中

失效是前綴階層，不是整包一律重算，也不是末端還能活著。順序固定為 `tools` → `system` → `messages`。某一層改了，該層與其後全部失效，更早的 breakpoint 仍可命中。改 tool definitions（名稱、描述、parameters）使三段一起失效。Web search 開關、citations 開關，以及 `speed: "fast"` 與標準速度切換，使 system 與 messages 失效、tools 仍在，因為前兩項會改寫 system prompt。`tool_choice` 與在 prompt 任何位置增刪圖片只失效 messages；圖片像素不同則另外由 exact match 處理。`disable_parallel_tool_use` 也只動 messages。Thinking 的 mode 與 extended 的 `budget_tokens` 會被 render 進 prompt，messages 一定失效；若該模型把設定畫在 tools 或 system 之前，那兩層也失效。`output_config.effort` 相同，但明確設成該模型預設值等同省略，不失效。支援 per-message effort 時，把 effort 放在 `messages` 裡的 `role: "system"`，已快取前綴維持有效（[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)；[Tool use with prompt caching](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-use-with-prompt-caching)）。

`temperature`、`top_p`、`top_k`、`max_tokens` 不在失效表裡，也沒有句子說它們在或不在 cache key。表是「哪些頂層參數會被畫進前綴」的清單，不是全部欄位的封閉集合，不能反推表上沒有的欄位一定不影響 hash。`tool_use` 的 JSON key 順序不穩定（文件點名 Swift 與 Go）會拆掉 cache。System 用字串或 typed block 陣列是不同形狀。Beta header 字串本身沒有被列成獨立失效列；會失效的是 header 所代表的行為改寫了實際進前綴的內容。Prompt caching 自 2024-12-17 GA 起不再需要 `prompt-caching-2024-07-31`。1 小時 TTL 自 2025-08-13 起不再需要 `extended-cache-ttl-2025-04-11`。現行指南的 1 小時範例只要求 `ttl: "1h"`。有人主張 2026-03-06 起預設從 1 小時被改回 5 分鐘，並使用 `ttl: 3600`；第一方時間線相反，預設一直是 5 分鐘，1 小時從 2025-05-22 起是 opt-in，那個整數 TTL 也與現行 `"5m"`／`"1h"` 不符（[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)；[Anthropic 貼文，2025-05-22](https://x.com/AnthropicAI/status/1925633128174899453)）。

Thinking block 不能直接標 `cache_control`，但出現在先前 assistant turn、並隨後續請求原樣重送時，會跟其他內容一起進前綴。文件有一句說，在帶 tool result 的後續呼叫裡，thinking 會作為請求內容被快取，而且即使沒有 explicit `cache_control` 也會發生。這句與「沒有 `cache_control` 就完全不快取」並陳，適用範圍是 thinking 被原樣帶回、且模型保留 thinking 的路徑，不是一條通用的隱藏 tail cache。Opus 4.5 與之後、Sonnet 4.6 與之後、Haiku 5.5 預設保留 thinking，非 tool-result 的新 user 內容不會因此拆掉舊 thinking。更早的 Opus、Sonnet，以及到 Haiku 4.5 為止，會剝掉先前的 thinking，其後 messages 移出快取。Fable 5.1、Mythos 5.1、Opus 5.5、Sonnet 5.5、Haiku 5.5 若 API 丟掉接收模型讀不了的 thinking block，前綴從該 block 起改變。`prefix_mismatch_behavior` 設成 `drop_block` 時，cache 從編輯點重來。Sonnet 5.5 的 thinking block 只在產生它的 account 或與其連結的 account 有效，別的 account 送回時會在模型看到之前被丟棄（[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)；[Release notes，2026-09-28](https://platform.claude.com/docs/en/release-notes/overview)）。

中途指令不該去改頂層 `system`。即使只追加一句，hash 就不同，system 與其後的 messages 都 miss。支援的模型改為在 `messages` 末端追加 `{"role": "system"}`，已快取前綴仍匹配。此能力列在 Fable 5.1、Mythos 5.1、Fable 5、Mythos 5、Opus 5.5、Opus 4.8、Opus 5、Sonnet 5.5、Haiku 5.5，明文不適用於 Sonnet 5。頂層 automatic caching 在選斷點時會跳過這種 turn-scoped system 訊息。清掉它的那一次請求，可重用的前綴停在它前面的 user turn，中間那個 assistant turn 會重算。改或刪已經送出的 mid-conversation system message，從該點往後失效。`inline-tools-2026-09-15` 可用 `tool_addition` 在中途加工具而不改 `tools` 陣列；例外是 `tools` 裡還沒有任何 non-deferred tool 時，第一次這樣定義會整段 miss 一次。`defer_loading` 的工具不進 system 前綴，tool search 以 `tool_reference` 追加在對話裡，前綴不動。Task budget 的 countdown marker 跨請求對不上，客戶端若每輪改 `task_budget.remaining`，包含該值的前綴失效（[Mid-conversation system messages](https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages)；[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)；[Task budgets](https://platform.claude.com/docs/en/build-with-claude/task-budgets)）。

Context editing、compaction 與 memory 不是用來維持尾端命中。它們在刪或摘要歷史，並從被改寫的那個點打斷前綴。Context editing 的策略是 `clear_tool_uses_20250919` 與 `clear_thinking_20251015`，beta header 範例為 `context-management-2025-06-27`。編輯發生在伺服器、進模型之前；客戶端仍保留完整未改歷史。清 tool result 會使已快取前綴失效，官方建議用 `clear_at_least` 一次清到值得打斷的量：當次付 write，其後請求重用新前綴。Thinking block 留在上下文裡時 cache 仍在；被清掉時，cache 在清除點失效（[Context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)）。Server-side compaction 可在 compaction block 上放 `cache_control`，斷點落在摘要之後。若沒有另外的 system breakpoint，摘要會讓已快取的 system prompt 一起失效，所以應在 system 結尾再放一個斷點，compaction 之後只 write 摘要、system 仍 read（[Compaction](https://platform.claude.com/docs/en/build-with-claude/compaction)）。

Claude Code 的 `/compact` 用摘要取代訊息歷史，對話層前綴對不上，這是設計如此。System prompt 層仍重用，除非這次是 resume 時仍帶著原本會變的舊 system prompt，第一次 compact 才換成現行 prompt 並重建該層。專案上下文從磁碟重載，只有 CLAUDE.md 與 memory 和 session 開始時相同才命中。摘要請求本身是 cache-safe fork：同一 system prompt、tools 與 history，把摘要指示當成最後一則 user message 附加。Cache 還熱時，這次請求讀前綴，費用主要在生成摘要；超過 TTL 之後，摘要請求把整段歷史當未快取 input。工程文把同一做法寫成：用與父對話完全相同的 system prompt、user context、system context 與 tool definitions，先接上父對話的訊息，再把 compaction prompt 附加成新的 user message。另開一支不帶 tools 的「summarize this」會對不上前綴，是他們點名的成本陷阱（[How Claude Code uses prompt caching](https://code.claude.com/docs/en/prompt-caching)；[Lessons from building Claude Code](https://claude.com/blog/lessons-from-building-claude-code-prompt-caching-is-everything)）。`/rewind` 把對話截回較早一輪，剩下的歷史就是當時建 cache 的內容，所以命中較早的條目；之後每一輪都讀過那個前綴，即使原輪已超過 TTL 也會被刷新。`/recap` 只附加摘要，不取代歷史。在 1 小時 TTL 上閒置時，Claude Code 可能在到期前自動 compact，`idleCompaction: false` 可關（v2.1.290 起）。Session 中途改 CLAUDE.md 不打破當下 cache，但也不生效。Auto memory 在 project context 層，於 session 開始或 `/clear`、`/compact` 之後才換。Memory 這個工具沒有被列成會單獨使 system cache 失效的開關；它的讀寫是否插入會改 hash 的系統區塊，文件沒有寫。

Cache diagnostics 不是第二條命中路徑。帶 `diagnostics` 時，API 依回應 `id` 存輕量 fingerprint，下次帶上一個 `id` 就回傳第一個分歧點：`model_changed`、`system_changed`、`tools_changed`、`messages_changed`，或 `previous_message_not_found`。Fingerprint 只有 hash 與 token 估計，不含原文，範圍是 organization 加 workspace，而且「比較的是請求結構，與該次是否真的 hit 無關」。結構相同仍可能因過期而 read 為 0。此功能只在 Claude API，2026-09-23 起不再需要 `cache-diagnosis-2026-04-07`（[Cache diagnostics](https://platform.claude.com/docs/en/build-with-claude/cache-diagnostics)）。SDK issue #1547 曾回報只在 system block 放 explicit breakpoint 時，伺服器仍對 user 內容多寫一筆；Anthropic 回覆那是已修的 bug。修後與「只在你的斷點寫入」一致，否定了「斷點之後還有隱藏尾端寫入」的現行行為（[anthropic-sdk-python#1547](https://github.com/anthropics/anthropic-sdk-python/issues/1547)）。

## 開源引擎自動認滿頁，Anthropic 只在斷點寫一筆

vLLM 與 SGLang 到 2026 年 10 月用同一個 engine 進程服務多個使用者：所有請求進同一條佇列與同一個 running batch，向開機時劃好的單一 GPU KV 池要記憶體，預設在 token 前綴相同時跨使用者共享，沒有 per-user 配額。隔離要呼叫端自己帶 `cache_salt`。vLLM 的 Automatic Prefix Caching 在 V1 預設開啟，只快取滿塊，鍵是父塊 hash、本塊完整 token ids 與 extra keys；差一個 token，從該塊起到後綴一起 miss，不滿的尾巴不能給下一筆用。同一 batch 裡剛滿的塊會立刻進 cache。SGLang 預設是 `UnifiedRadixCache`，CPU 上的 radix tree 只存 GPU pool 的 index，`match_prefix` 走最長相同前綴，命中停在節點中間就 split；`--page-size` 預設 **1**，可以在 token 邊界切開，頁放大之後才退回只認整頁，不滿一頁的尾巴不進樹。多輪沒有伺服器端對話物件，客戶端每一輪都要重送完整 prompt（[prefix caching design](https://docs.vllm.ai/en/latest/design/prefix_caching.html)；[Server Arguments](https://docs.sglang.io/docs/advanced_features/server_arguments)；[radix_cache.py](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/mem_cache/radix_cache.py)）。

三邊相同的是：匹配單位是前綴而不是後綴，前面任一處不同就讓後面全部失效，客戶端必須重送會被比對的那段 bytes。Anthropic 的 20-position lookback 是唯一偏離「只比對你標的那一個 hash」的官方規則，但它仍只接受某個更短前綴的、而且更早 breakpoint 寫過的 hash。它不是 suffix match，也不是 SGLang 那種任意 token 邊界的 radix。第三方把 Anthropic 說成 vLLM prefix cache 或 RadixAttention，並自行補上 LRU，那些句子沒有 Anthropic 出處。第一方只說記憶體中的 KV 表示加上 cryptographic prefix hash、exact prefix match，以及最小 TTL（[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)）。

差別在寫入粒度、誰可以共享，以及淘汰有沒有被寫成政策。vLLM 對每個滿塊自動建條目，SGLang 在 `page_size == 1` 時幾乎每個 token 邊界都能進樹，而且 `checkpoint()` 可以在請求結束前就把已算出的前綴插進樹，讓另一個使用者不必等這筆請求結束。Anthropic 只在呼叫端（或已啟用 caching 後的 server-tool 自動斷點）指定的位置寫一筆，條目要等第一個回應開始才可供後續請求使用。斷點之前的穩定內容不會被補寫。因此「尾巴」在 Anthropic 是你選擇的寫入點：放對了，下一輪用 lookback 讀回整條舊鏈，只為新增長的一段付 write；放在每輪都變的最後一塊上，整段前綴每輪都是新 hash。vLLM 不滿塊的尾巴本來就不能共享；SGLang 預設可以把那個尾巴切進樹。Anthropic 放在最後一個斷點之後的 varying suffix 根本不是條目，別的請求無法靠它命中。

共享的預設方向相反。未加 salt 的 vLLM 與 SGLang 在同一進程裡讓不同使用者的相同前綴進同一塊或同一個節點。vLLM 把這件事寫成時序側信道：前綴只有很少 token 時，TTFT 的差就幾乎能判斷別人的快取裡有沒有這段，文件給的緩解是每個請求帶秘密 `cache_salt`，混進第一個塊的 hash。Salt 不把別的租戶的 KV 從 GPU 抹掉，池仍然共用（[Security, v0.31.0](https://docs.vllm.ai/en/v0.31.0/usage/security/)）。Anthropic 沒有 salt 欄位。隔離寫在存取範圍裡：workspace，或 Bedrock／Google Cloud 文件所說的 organization，再被 Vertex 的 project 與 AWS 產品頁的 account 改寫。邊界內不需要、也沒有開關去拒絕共享；邊界外相同的 system prompt 不會互相省錢。把 Claude Code 的 “globally cached” 讀成跨客戶共享，超出第一方合約。

淘汰也沒有被寫成同一件事。vLLM 在 free queue 上偏置 LRU，請求末端 hash 了更多 token、較不容易被重用，釋放時反序入隊，所以先被趕走的是沒人引用的獨特尾巴，共享前段活得較久。正在跑的請求放不進池時，V1 預設丟掉 GPU block 再重算，不是 swap。SGLang 預設也是 LRU，從葉往根收；eviction 文件另列 `tlru`，先丟對話裡下一輪用不到的尾端。那是開源樹上的打分政策，仍是前綴節點，不是後綴索引，而且 server arguments 表沒有把它列進 choices，不能把它說成已核對的預設 CLI（[prefix caching design](https://docs.vllm.ai/en/latest/design/prefix_caching.html)；[Radix Cache Eviction Policies](https://docs.sglang.io/docs/advanced_features/radix_eviction_policy)）。Anthropic 公開的只有最小 TTL。沒有最大條目數、每 workspace 配額、LRU／LFU 的政策名，也沒有寫同一前綴同時存在 5 分鐘與 1 小時條目時命中選哪一筆，除了混用 TTL 的 A／B／C 計費位置。容量導致的非 TTL miss 沒有比例可引。

## Conclusion

要讓使用者口中的「尾巴」真的管到命中，操作對象不是一段可獨立檢索的末端 KV，而是這次請求願意凍結的最後一個 block。斷點放在下一輪仍會原樣重送的位置，每輪新增維持在 20 個 position 以內，或事先在較早的位置再留一個斷點，下一輪就會讀回整條舊鏈，只為新長出來的那一段付 write。斷點若落在 timestamp 或本輪使用者原文上，automatic caching 會忠實地每輪重寫，lookback 幫不上忙。前綴中間一改，從該點到末端一起作廢；compaction 與 context editing 的價值是少改，或用 cache-safe fork 一次改完再建立新前綴，不是在前綴變了之後保住尾端。

和開源引擎並排之後，調參手冊是反的。vLLM 與 SGLang 要決定的是頁有多大、salt 放哪、池滿了先丟誰。Anthropic 不公開這些旋鈕，卻把隔離、最短 TTL 與「只在斷點寫一筆」寫進合約。Workspace 內的相同工具定義與 system prompt 會在使用者之間互相省 prefill，這是功能而不是漏洞頁上的側信道；workspace 之外則沒有未加鹽引擎那種默認共享。沒有人能手動清掉一筆、也不能向文件要求容量壓力下仍活滿 5 分鐘。Harness 該排列的是 bytes 與 breakpoint，不是一顆看不見的 page size。
